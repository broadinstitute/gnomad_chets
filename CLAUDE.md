## What this repo does

`v2/` contains the production v2 phasing / variant-cooccurrence pipeline ([Guo, Francioli et al., *Nat Genet* 2024](https://www.nature.com/articles/s41588-023-01608-3)). The phasing logic in `phasing.py` is the historical reference; `compute_gnomad_phase.py` is the orchestration entry point.

`v4/` contains the in-progress port to gnomAD v4 plus the in-trans observed-vs-expected (in-trans-OE) depletion feature. The main scripts:

- `v4/create_vp_list.py` — builds the sites HT, variant-filter HT, filtered VMT, and variant-pair list from gnomAD v4 exomes (the upstream steps).
- `v4/compute_vp_counts.py` — consumes the variant-pair list and produces the per-pair genotype-counts table (multi-step; see below).
- `v4/run_in_trans_oe.py` — consumes the gt-counts table, computes per-candidate in-trans depletion against ClinVar P/LP partner sets.

`analysis/` holds one-off characterization scripts and reports, one folder per topic; `analysis/README.md` indexes them.

## v4 pipeline architecture

The pipeline is a chain of flags in dependency order. The upstream group runs in `create_vp_list.py`; the counts group in `compute_vp_counts.py`:

| script | flag | input | output |
|---|---|---|---|
| create_vp_list | `--preprocess-sites-ht` | gnomAD VEP / freq / final-filter | `sites.{postfix}.ht` |
| create_vp_list | `--create-variant-filter-ht` | sites HT | `variant_filter.{postfix}.ht` |
| create_vp_list | `--filter-vmt` | gnomAD VDS, filter HT | `filtered_vmt.{postfix}.mt` |
| create_vp_list | `--create-variant-pair-list-ht` | filtered VMT, filter HT | `variant_pairs.{postfix}.ht` |
| compute_vp_counts | `--encode-genotypes` | gnomAD VDS, pair list | `genotype_count_intermediates.{postfix}/...` (var_idx + encoded gt sets) |
| compute_vp_counts | `--build-variant-size-info` | encoded intermediates, pair list | `variant_size_info.{postfix}.ht` |
| compute_vp_counts | `--compute-counts-light` / `--compute-counts-heavy` | encoded intermediates, pair list, size-info | `.../counts_{light,heavy}.ht` |
| compute_vp_counts | `--combine-counts` | light + heavy counts | `variant_pairs.genotype_counts.{postfix}.ht` |
| compute_vp_counts | `--split-encode-by-pop` | encoded intermediates of a subset / cohort | `genotype_count_intermediates.{postfix}.{qualifier}.{group}/` (one re-indexed encode per gen-anc group) |
| compute_vp_counts | `--merge-subset-counts` | per-subset counts HTs (`--merge-by-pop`: the 18 per-group strata) | `variant_pairs.genotype_counts.{postfix}.ht` (`--merge-by-pop` adds `gt_counts_by_pop`) |

`--encode-genotypes` densifies only the pair-list variants out of the VDS in-memory (transient scratch checkpoint, no persisted dense MT) before encoding — there is no separate dense-MT step. It also keeps read-backed phase (`PGT` + `PID`) and stores a per-variant `phased_het` sidecar (`sample_idx → {pid, gt0}`); the full-cohort count steps then emit `n_phased_cis` / `n_phased_trans` (default on via `--emit-phase-counts`), the physical-phase split of the double-het `AaBb` cell — the same signal the gnomAD MNV pipeline derives. Per-pop counts (`--stratify-by-pop`) don't carry phase yet, and phase is not yet consumed by `phase_gnomad.py` / `in_trans_oe.py`. `--encode-genotypes` also applies the **v4 high-AB het → hom-alt correction** (see gotcha below), so it now joins the release freq HT (`get_freq`, per-variant `af`) and the meta HT (per-sample `fixed_homalt_model`).

The full-cohort count steps also accept **`--emit-no-pbt-counts`** (with `--trio-set {pedigree,trios}`, matching `trio_phasing.py`): they additionally emit `gt_counts_raw_no_pbt` / `gt_counts_adj_no_pbt` — the 9-cell counts with the PBT (trio) members subtracted out (`release \ PBT`). Mechanism: the count step **restricts the same encode to `PBT∩cohort` once** (`restrict_encoded_to_samples` — re-indexes the sets to a dense PBT space, checkpointed) and counts it to `counts_pbt.ht`; `--combine-counts` then subtracts element-wise (`_subtract_pbt_counts`). This is **exact for all 9 cells, AABB included** (disjoint-cohort additivity — see the PBT-exclusion gotcha); both arrays come from the same encode so they share the identical adj + high-AB classification. **Why restrict-once, not per-pair**: the earlier count-time version embedded an `hl.literal(PBT∩release index set)` in the per-pair count expression, which Hail replicated into every light/heavy task and blew past `spark.rpc.message.maxSize` (835 MB/task). The keep-set literal now lives only in the one checkpointed re-index transform (`_restrict_encoded_to_indices`, shared with `restrict_encoded_to_pops`). `trio_phasing.py --gnomad-counts-no-pbt --gnomad-counts-path <that HT>` then reuses these columns directly — no separate gnomAD-no-PBT densify/count pass. Full-cohort only (incompatible with `--stratify-by-pop`).

**By-sample subsetting (`--vds-subset` / `--merge-subset-counts`)** splits the expensive densify+encode+count across a disjoint by-sample partition of the cohort and sums the results back. Julia pre-split the raw v4.0 exomes VDS (`gs://gnomad/v4.0/raw/exomes/gnomad_v4.0.vds` — what `get_gnomad_v4_vds` reads) into 10 column subsets: `non_ukb` + `ukb.<group>` for the 9 v4 gen-anc groups (`resources.get_count_subsets` / `get_count_subset_vds_path`). `compute_vp_counts --vds-subset <name> --encode-genotypes …` reads that subset VDS by path (`_read_count_subset_vds`: same release/HQ meta semi-join + interval + chr19-multiallelic-drop as the full loader, handed to `densify_encode_input_mt` via its new `vds=` param), and writes **subset-qualified** count-group outputs (`genotype_count_intermediates.{postfix}.{subset}/`, `variant_pairs.genotype_counts.{postfix}.{subset}.ht`) via `get_variant_pair_resources(subset=…)` — the pair-list/filter **inputs stay the full-dataset artifacts** (subsetting is counts-only; the pair list is always built on everything). `--merge-subset-counts [--merge-subsets a,b,…|all]` then element-wise-sums the per-subset count HTs (`merge_subset_counts`) into the plain full-cohort path — **exact for all 9 cells incl. AABB** by disjoint-cohort additivity, GIVEN two things: (1) every subset carries every pair-list variant as a row (the v4.0 splits preserve all variant rows — see `analysis/pipeline_runs/ukb_vds_split_runs.md`; the `ukb.vds` intermediate has since been deleted), and (2) **the release/high-quality restriction is applied AFTER densify, not on the sparse VDS.** That second point is the subtle part: `hl.vds.filter_samples` on the sparse VDS PRUNES any variant row with zero entries among the kept samples, so restricting the subset to release *before* densify drops the row (and hence the hom-ref baseline) of every pair-list variant monomorphic within that subset — which for a small subset is most of them. A MatrixTable `filter_cols` (unlike `filter_samples`) keeps every row, so `_read_count_subset_vds` restricts to release with the gnomad_qc `split_vds` idiom — `filter_cols` to the cohort on BOTH `variant_data` and `reference_data`, prune now-empty reference blocks, reconstruct the VDS — before densify; `to_dense_mt` then fills the monomorphic-in-subset sites hom-ref from the reference blocks. (Densifying the whole subset and restricting columns on the dense MT afterward is equally correct but wastes work densifying non-cohort samples; see `knowledge/vds.md` in gnomad_methods.) Diagnosed on CAPN3 (2026-08-31): the pre-fix version undercounted AABB (merged ≈ ¼ of full on rare pairs, `gt_counts_adj` matched only 10,060/70,492) because `_read_count_subset_vds` did `filter_samples(release)` up front — staged row counts showed raw `ukb.mid`=11,699 rows over CAPN3, `to_dense_mt`=11,699 (preserved), but `filter_samples(release)`=290. **Validated after the fix (2026-09-01):** all 10 subsets → merge → diff vs a full-cohort CAPN3 run is **bit-identical on every one of the 70,510 pairs the full run emits** (raw + adj + phase, 0 mismatches), no subset dropping any pair. The merge additionally keeps 744 pairs the **full run itself drops** — `get_gnomad_v4_vds`'s pre-densify `filter_samples(release)` prunes pair-list variants that have zero release carriers in the VDS (freq-based pair list vs VDS-release cohort mismatch), which the densify-then-restrict subset path retains as inert all-hom-ref pairs; so the merge is exact on the full run's universe and a strict superset of it. Exomes only; incompatible with `--stratify-by-pop` / `--pops` / `--emit-no-pbt-counts` (run those on the merged full-cohort counts).

**Per-group counts (`--split-encode-by-pop`, `--merge-by-pop`).** Each `ukb.<group>` subset holds one group, but `non_ukb` holds all nine. `--vds-subset non_ukb --split-encode-by-pop` restricts the one non_ukb encode to each group (`split_encoded_by_pop`, the re-index-once of `restrict_encoded_to_pops`) and writes `genotype_count_intermediates.{postfix}.non_ukb.{group}/`; each group is then counted with `--count-cohort non_ukb.{group}` through the normal size-info → light / heavy → combine steps, read-backed phase included. `--merge-subset-counts --merge-by-pop` sums the 18 strata (`resources.get_count_strata`: `ukb.<group>` + `non_ukb.<group>`) into the full-cohort table and adds `gt_counts_by_pop` (`dict<pop, struct{raw, adj, n_phased_cis, n_phased_trans}>`, `all` included), the layout `phase_gnomad.py` reads. Exact by the same disjoint-cohort additivity; a sample with no group label is an error, since it would silently drop out of the sum. **Trio members per subset:** `--count-pbt-members` (any count cohort, `--trio-set`) restricts that cohort's encode to its PBT members and counts them, phase included, to `counts_pbt.ht` beside the encode (empty when the cohort has none; `--emit-no-pbt-counts` now runs the same step); `--merge-subset-counts --merge-no-pbt` merges those per group and subtracts, adding `gt_counts_{raw,adj}_no_pbt`, `n_phased_{cis,trans}_no_pbt` and `gt_counts_by_pop_no_pbt` plus the `no_pbt_trio_set` / `n_pbt_samples` globals. `trio_phasing.py --gnomad-counts-path` reads those, per group too with `--stratify-by-pop`; `trio_phasing.py --chr chrN --vp-list-path <production pair list>` builds the trio truth on the same pairs as the counts.

**`--count-cohort NAME`** qualifies the count-group outputs as `.{NAME}` exactly as `--vds-subset` does (same `get_variant_pair_resources(subset=…)` plumbing), but without reading a subset VDS — for counting several cohorts against one shared pair list (e.g. chr21 `s1` / `s2`). Pass it identically to every count step. **`--dense-mt-path`** (with `--encode-genotypes`) encodes from an existing dense MT instead of densifying the VDS: `restrict_dense_mt_for_encode` restricts rows to the pair-list variants and columns to release / high-quality via `semi_join_cols` (a MatrixTable column filter, so no row pruning), then applies the same `annotate_encode_input_mt` as the densify path. The MT must carry `GT/GQ/DP/AD/PGT/PID/_het_non_ref` (an `export_for_phasing --checkpoint-mt` output does; a GT-only VCF export does not). Any other exclusion baked into it (e.g. trio members) is inherited, not re-applied. **`--counts-release-only` is a `BooleanOptionalAction` that defaults to TRUE** (counts are on release, as production's are), so omitting it does *not* select high-quality — pass `--no-counts-release-only` for that. The chr21 S1 encode was first launched without it and silently cut to release (`120279 -> 75344`); check the `Dense MT restricted to the … cohort: A -> B samples` log line before trusting an encode.

**`--chr chrN`** (compute_vp_counts) counts one chromosome against the chrom-sharded pair list `exomes.variant_pairs.chrN.ht` that `create_vp_list --chr` writes. It appends `.chrN` to the postfix (counts land at `…genotype_counts.chrN[.{subset}].ht`), limits the encode's VDS read to the chromosome, and takes size-info `gene_id` from the unsharded `exomes.variant_filter.ht` the shard was built from. The shards are keyed by `vp_ht_idx`, not locus, so `hl.filter_intervals` raises on them; no cut is needed, since each holds one chromosome. Pass it to every step.

`run_in_trans_oe.py` then runs `annotate_pair_oe_terms` → `aggregate_oe_per_candidate` → output HT.

`phase_gnomad.py` runs `hl.experimental.haplotype_freq_em` on the gt-counts HT. By default it repartitions/checkpoints the input to balance the EM shuffle, but if the input's native partitioning is already good (e.g. a freshly-written HT from a Tier 3 post-hoc fix or from `--compute-counts-per-sample`) you can pass `--em-partitions 0` to skip the shuffle entirely. Bounding partition count also caps worst-case per-partition wall time if EM stalls (see the `haplotype_freq_em` gotcha below).

### Trio phasing (`trio_phasing.py`)

`v4/trio_phasing.py` consolidates the whole v2 trio/PBT analysis (`phase_by_transmission.py` + the `create_pbt_*` steps in v2 `create_vp_matrix.py` + `chet_utils` helpers + the gnomAD-comparison export) into one script (resources via `get_trio_phasing_resources`). It **reuses** the v4 counts machinery and EM phasing rather than duplicating: imports `create_variant_pair_ht` from `create_vp_list.py`, `create_variant_pair_filter_ht` / `filter_pairs_by_an_pct` / `encode_genotypes` / `count_all_pairs_via_index` from `compute_vp_counts.py`, and `get_phased_gnomad_ht` from `phase_gnomad.py`.

Trio side (high-quality samples, incl. unreleasable):

| flag | input | output |
|---|---|---|
| `--create-pbt-trio-matrix` | gnomAD VDS, `gnomad_qc.v4` finalized pedigree | `pbt_trio_matrix.{postfix}.mt` |
| `--explode-pbt` | PBT trio matrix | `pbt.{postfix}.mt` |
| `--phase-multi-families` | exploded PBT MT | `pbt_multi_families.{postfix}.mt` |
| `--derive-trio-vps` | PBT MT (probands), variant filter HT | `trio_variant_pairs.{postfix}.ht` |
| `--call-trio-chet` | PBT MT (probands), trio VPs | `trio_phase_counts.{postfix}.ht` (per-pair `n_same_hap`/`n_chet`) |

Comparison side (gnomAD = `release_only`, **all PBT trio members removed**):

| flag | input | output |
|---|---|---|
| `--gnomad-counts-no-pbt` | production counts HT w/ `_no_pbt` cols (`--gnomad-counts-path`) **or** gnomAD VDS + trio VPs (from scratch) | `gnomad_no_pbt.genotype_counts.{postfix}.ht` |
| `--phase-gnomad-counts` | gnomAD-no-PBT counts | `gnomad_no_pbt.phased.{postfix}.ht` |
| `--export-comparison` | trio truth + gnomAD phase | `trio_comparison.{postfix}.ht` + `.tsv` |

(All trio-phasing outputs are additionally suffixed with `.{trio_set}` — see `--trio-set` below — e.g. `pbt_trio_matrix.{postfix}.pedigree.mt`. The shared variant-filter HT input keeps the plain `{postfix}`.)

Notes:
- The v4 VDS is read split, so no `split_multi_hts` pass is needed (unlike v2). Uses Hail built-ins `phase_trio_matrix_by_transmission` + `explode_trio_matrix` directly. This matches `gnomad_qc.v4` `generate_variant_qc_annotations.run_generate_trio_stats` (densify → adj → `trio_matrix(complete_trios=True)`); that path drops multiallelics whereas we split them.
- **`--trio-set {pedigree, trios}`** (default `pedigree`) selects the pedigree resource: `pedigree()` = all trios, multiple offspring per family (n=15061, the v2 default `fam_path` and what the existing trio stats were run on) vs `trios()` = one random trio per family (n=12731, the v2 `true_trios=True` analog). The value is folded into every trio output path so the two sets never overwrite each other. There is **no separate parent-pair dedup** — family deduplication is expressed solely by choosing `trios`; probands are simply the `s == source_trio.id` columns of the chosen set.
- The finalized pedigree is **exomes-derived** in gnomad_qc v4.
- **No persisted dense trio MT / PBT trio matrix exists in v4 to reuse** — `identify_trios.run_mendel_errors` and `generate_variant_qc_annotations.run_generate_trio_stats` both densify the trio MT transiently and only write aggregate HTs (`ped_mendel_errors`, `trio_stats.ht`). `--create-pbt-trio-matrix` is the first persisted one.
- PBT-sample exclusion from the gnomAD counts uses **subtraction from the same release encode**: `release \ PBT = release − (PBT∩release)`, element-wise on the 9-cell arrays. This is **exact for all 9 cells, AABB included** — every cell is an additive per-sample count over the disjoint cohorts (`release = (release\PBT) ⊎ (PBT∩release)`), and the AABB `n_samples` baseline (`AABB = n − |D'_v1 ∪ D'_v2|`) also splits additively across them. The one requirement is that both arrays use the **same genotype classification** (same adj + high-AB correction), so a sample lands in the same cell in both — guaranteed by computing both from the *same* release encode. `--emit-no-pbt-counts` therefore restricts that encode to the (small) `PBT∩release` cohort **once** (`restrict_encoded_to_samples`, re-indexed + checkpointed), counts it to `counts_pbt.ht`, and subtracts at `--combine-counts` (`_subtract_pbt_counts`); it must NOT be sourced from a separately-built MT with a different adj/correction. **Do not** put the PBT-index-set as an `hl.literal` in the per-pair count expression — Hail replicates it into every count task and it blows past `spark.rpc.message.maxSize` (that footgun is why the restriction is a one-shot re-index, not a per-pair intersect). The production run (`compute_vp_counts --emit-no-pbt-counts`) does this; `trio_phasing.py --gnomad-counts-no-pbt --gnomad-counts-path <that HT>` then reuses the emitted `_no_pbt` columns directly (restrict to trio VPs, promote to `gt_counts_{raw,adj}`) — no densify. Its from-scratch fallback (omit `--gnomad-counts-path`) instead densifies release-minus-PBT via `hl.vds.filter_samples(keep=False)`.
- Per-pop stratification is **not** implemented yet (full-cohort only); the schema/flow leaves room to add it.
- `--phase-multi-families` builds its consensus over `PBT_GT`; the v2 original collected the unphased `GT`, which made its phased-vote sort a no-op.
- `hl.vds.filter_samples` must **not** be called with `remove_dead_alleles=True` on a split VDS — split data has no `LA` field, so it raises `AttributeError: ... 'LA'`.

`v4/resources.py` is the single source of truth for paths and constants:
- `DEFAULT_TMP_DIR = gs://gnomad-tmp-30day` (scratch)
- `VARIANT_COOCCURRENCE_ROOT = gs://gnomad/v4.1/variant_cooccurrence` (production)
- `_get_resource_path` builds `{output_dir}/{data_type}.{resource_name}.{output_postfix}.{ext}`. The `{output_postfix}` argument is **prepended verbatim** — if you pass `--output-postfix sgca_v9_oe_extra_6_12`, you get e.g. `exomes.variant_pairs.sgca_v9_oe_extra_6_12.ht`. The script does **not** auto-prepend a gene name; the gene goes in the postfix.
- `TEST_INTERVALS` maps gene symbol → interval string (used by `--gene <SYMBOL>` to scope all HTs/VDSes).

## Code conventions

Match the existing style in each file rather than imposing new ones.

- Utils functions are pure transformations: HTs in → HTs out. All file I/O lives in CLI scripts.
- Utils functions taking a single Hail Table name the parameter `ht`; use descriptive names only when taking multiple HTs.
- Top-level imports only. Don't add lazy imports unless needed to break a circular import. Right now there are none — `v4/in_trans_oe.py` no longer imports from `v4/create_vp_list.py`; the OE variant-filter-HT builders live in `create_vp_list.py`.
- Don't add docstrings, type annotations, or comments to code you didn't touch. Comments should explain *why*, not what.
- Don't add backwards-compatibility shims. If something is removed, delete it cleanly.

## Hail / pipeline gotchas

These have all bitten the v4 pipeline at some point.

- **`gt_counts_adj` is `array<int64>`**, but `hl.experimental.haplotype_freq_em` requires `array<int32>`. Cast explicitly: `gt_counts.map(hl.int32)`.
- **`p_chet` can be NaN** when EM denominators collapse (e.g., zero double-het pairs). Guard with `hl.if_else(hl.is_nan(p_chet), hl.missing(...), p_chet)`, or equivalently set `o_pair = 0` when `double_carriers == 0`.
- **Pair list is keyed `(locus1, alleles1, locus2, alleles2)` with `v1 ≤ v2`**. The candidate may appear as either `v1` or `v2`. Aggregations need to handle both orientations (`view_a ∪ view_b`).
- **`filter_pair_ht_to_in_trans_oe_pairs`** drops pairs where **both** sides are OE-candidate-only (i.e., source ⊆ `{in_trans_oe_candidate, in_trans_oe_intronic_padding}`). The intent is to avoid candidate × candidate explosion while preserving (OE-candidate × P/LP-partner) pairs.
- **Cache before group-by shuffles**. `pairs = pairs.cache()` before `pairs.group_by(...)` prevents intermittent shuffle errors on the Spark backend.
- **Hail expression source-tracking after `.filter()`**: when you filter a Table and then refer to its fields, bind the filtered Table to a new variable — `ht_sub = ht.filter(...); ht_sub.select(x=ht_sub.foo)`. Re-using `ht.foo` after a filter triggers `Cannot combine expressions from different source objects`.
- **Table indexing requires expressions, not Python literals**. `ht[locus, alleles]` works only if `alleles` is an `hl.literal([...])` or a column expression — passing a plain Python list raises `Cannot index with a scalar expression`.
- **The count steps read the encoded intermediates + size-info from disk; they don't re-encode.** `--encode-genotypes` overwrites `var_idx.ht` + `encoded_gt_sets_by_var_idx.ht` under `genotype_count_intermediates.{postfix}/` on every run (`overwrite=True`), so there's no stale-cache trap within a step. But if you change the pair list or `--min-an-pct`, you must re-run `--encode-genotypes` (and `--build-variant-size-info`) before re-running counts — otherwise `--compute-counts-{light,heavy}` count against the previous run's variant set. Symptom: high-AF candidates with hundreds of pair-list entries but zero gt_counts entries.
- **No-entry (uncallable) samples must stay out of the AABB (hom-ref/hom-ref) cell.** `_count_from_sets` (the shared light/heavy/per-pop kernel) derives AABB from the global `n_samples` as `n_samples − |D'_v1 ∪ D'_v2|` (plus F terms for the raw cell), where `D'_v = all_samples ∪ raw_hr_adj_missing = cats 1-6`. Correctness hinges on the encoder putting **cat 1 (no-entry) samples in `all_samples`**: because they're in `D'_v` they fall outside `H_v = N \ D'_v` (the adj-PASS-0/0 hom-ref set), so a sample with no GT at either variant is never counted as hom-ref. If `_encode_genotype_sets_by_var_idx` ever stopped including no-entry samples in `all_samples`, they'd leak into AABB and inflate it (and `sum(gt_counts)`, used as `n_pair`) at low-coverage positions (3' UTR etc.). Cheap CI check: `sum(gt_counts_adj) ≤ n_samples`.
- **AN_pct floor (`--min-an-pct`) is set at the encode step, applied at consumption, and may only be raised downstream.** The pair list stays the complete raw artifact (no floor baked in). `--encode-genotypes` filters pairs by `--min-an-pct` before densifying and stamps the floor directly onto the encoded HT's globals; each count step re-applies the filter (`filter_pairs_by_an_pct`) and asserts its floor is ≥ the encoded HT's stamped floor (`_assert_min_an_pct_not_lowered`). A lower downstream floor would count pairs whose variants were never densified — the guard turns that into a `ValueError`. Pass `--min-an-pct` *consistently* across the encode/count invocations (like `--output-postfix`). Default `0` drops endpoints with `an_pct == 0` — and since AN_percent is floored, that is AN below 1% of the maximum, not only AN = 0: in the 5-gene exome bundle it removed 26,353 pairs, 18,919 of them co-carried by a release sample. Pre-guard artifacts carry no global and are treated as floor `-1` (permissive).
- **Pairs whose variants are missing from the encoded MT are not real comparators** across counting methods. The pair list (`vp_ht`) is built upstream of the dense MT; some pair endpoints can be absent from the MT (different multi-allelic split, filtered out by `--min-an-pct`, etc.) so the `var_idx_ht[locus, alleles].var_idx` lookup returns NULL for those pairs. `compute_counts_light` / `compute_counts_heavy` now drop those pairs upfront and log the count via `_drop_pairs_missing_v_idx` — but the other benchmark methods (`approach_b`, `per_sample`, `v4_original` in `analysis/benchmarks/benchmark_single_gene.py`) each invent a *different* default cell when their inner lookup is missing: approach_b's set algebra propagates NULL into some cells but evaluates others to 0; per_sample collapses to `[NULL, 0, 0, …]`; v4_original treats every sample as filtered-out and dumps them all into AABB (≈ `n_samples` even though no GT data exists). Symptom seen on ANO5: `approach_b vs v4_original` reports `223 raw mism / 223 adj mism` on the full 22,155 pairs, but **0 mismatches** on the 21,932 pairs where both v_idx are defined. **When validating a new counting method, only diff cells on pairs where both variants are in `var_idx_ht`.** light_heavy's dropped-row count is the cleanest signal — if it doesn't match `vp_ht.count()`, the difference is the absent-from-MT pair count for that gene.
- **Encoded sets are stored positive form (no complement encoding).** `_encode_genotype_sets_by_var_idx` stores `all_samples` (cats 1,3-6) and `raw_hr_adj_missing` (cat 2) directly; cat 7 (adj-PASS-0/0 majority) is never stored — `_count_from_sets` reconstructs it as `N − (cats 1-6)` from `n_samples` via plain set-intersection algebra. The old "store the smaller of set/complement + `*_is_complement` flag" optimisation was **removed** (commit on `jg/v4-pipeline`): it halved worst-case row size but its proper-complement invariant (`stored = cat_2 ∪ cat_7`, not just `cat_7`) was a subtle, once-buggy footgun. Tradeoff: at very-low-AN variants the positive `all_samples` (large cat-1 no-entry) can approach `n_samples`, so run the count steps with a **non-zero `--min-an-pct`** to bound row/shuffle size. Invariant to keep: `sum(gt_counts_adj) ≤ n_samples` on any output HT (regression tests: `tests/v4/test_create_vp_matrix_unit.py::TestCountFromSetsRealData`, real chr19 fixtures normalised to positive form in the harness).
- **High-AB het → hom-alt correction (v4 consistency).** GATK <4.1.4.1 mis-called some true hom-alts as high-allele-balance hets; gnomAD v4 release freq corrects these ([`gnomad_qc` `generate_freq.py`](https://github.com/broadinstitute/gnomad_qc/blob/main/gnomad_qc/v4/annotations/generate_freq.py)). `_encode_genotype_sets_by_var_idx` mirrors it: a call is reclassified het→hom-var (`1→2`) when `GT.is_het_ref() & adj & (AD[1]/DP > HIGH_AB_CUTOFF=0.9) & ~_het_non_ref & ~fixed_homalt_model & (af > HIGH_AB_AF_THRESHOLD=0.01)`. **Applied to BOTH raw and adj**, matching the release: the finalized `freq` is `ab_adjusted_freq`, whose `correct_for_high_ab_hets` adds the (adj-determined) high-AB hom-alt count to *every* stratum including `freq[1]` = raw (the raw-group aggregate of the adj-gated `high_ab_het`). So a corrected call sits in `raw_hv` AND `adj_hv`. The raw reclassification is **gated on adj-pass** (`high_ab_homalt & adj_pass_expr`) — a non-adj high-AB het is not in gnomAD's correction set, so it stays het in raw. (`gnomad_qc`'s docstring says "raw is not adjusted" but the code + released data adjust it; verify against released `freq[1].AC` if in doubt.) Requires three inputs wired onto the dense MT by the encode step: per-variant `af` (release `get_freq().freq[0].AF`, same source as `create_vp_list`), per-sample `fixed_homalt_model` (`meta().project_meta`), and per-entry `_het_non_ref` (`LGT.is_het_non_ref()` captured **pre-split** in `_split_variant_data_keeping_phase`). The correction auto-skips when any of those fields is absent (e.g. the trio PBT MT), so `use_precomputed_adj` callers are unaffected. **Genomes (NOTE — decide before any release):** genomes metadata has no `fixed_homalt_model`, because the genomes correction was never per-sample — gnomad_qc v3.1's `hom_alt_depletion_fix` corrects every sample at AF > 0.01, AB > 0.9, not het-non-ref. The encode input therefore sets `fixed_homalt_model = False` for every genomes sample (`annotate_encode_input_mt`); leaving it *absent* would make the encoder silently skip the whole correction. But genomes currently use the **exomes** raw semantics — raw gated on adj, AF gate from the v4 genomes freq — so exome and genome counts stay comparable. The genomes release did it differently: v3.1 corrected every GT before computing freq (raw **ungated**) and gated on **v3.0** release AF. adj is unaffected beyond variants at AF ≈ 0.01, but `gt_counts_raw` is not an exact mirror of the genomes release. Settle this before releasing any genomes co-occurrence artifact. The `fix_freq_an.py` v4.0→v4.1 AN fix is **not** replicated — it was specific to per-subset (UKB/non-UKB) freq computation; we densify the full release cohort in one pass and use the corrected `all_sites_an` for `an_pct`.
- **Sex-ploidy adjustment (v4 consistency, sex chromosomes only).** `densify_encode_input_mt` applies `adjusted_sex_ploidy_expr(locus, GT, sex_karyotype)` right after densify — matching `gnomad_qc` `generate_freq` `densify_and_prep_vds_for_freq`, so adj + the high-AB correction are computed on the sex-adjusted GT (order: `_het_non_ref` pre-split → densify → sex ploidy → adj → high-AB). It's a **strict no-op on autosomes** (its first branch is `in_autosome`), so per-chromosome autosomal runs (the default plan) are unaffected; only chrX/chrY jobs change. On non-PAR X/Y: an XY call becomes haploid (`Call(gt[0])`) and an XY het is dropped to missing; an XX call on Y becomes missing. The existing classifier handles all three with no change: a **hemizygous alt (haploid `Call(1)`) → `is_hom_var` → the `aa`/`bb` hom cell** (the chosen co-occurrence modeling; note this makes its per-variant AC 2 not 1, so revisit if AC-matching on chrX is ever needed), a haploid ref → hom-ref, and a dropped het (missing GT, defined entry) → `raw_gt=0` → in `all_samples`/`n_with_data` but no genotype cell, so it's uncallable and excluded from AABB. Needs the per-sample `sex_karyotype` col (`meta().sex_imputation`). Sex chromosomes may still warrant bespoke handling (gnomAD's MNV pipeline punts on hemizygous modeling) — decide per chrX/chrY run.
- **`count_all_pairs_via_index` is only for the no-heavy case, and it inherits the pair list's partitioning.** Its docstring says to use it when `_size_info_to_heavy_variants` would be empty; at cohort scale it usually isn't. Calling it directly on a pair list that came off a dense MT means a handful of fat partitions, which both starves YARN of schedulable containers (the cluster never autoscales, and graceful decommission of a secondary worker loops forever) and puts hundreds of thousands of pairs in each task. Symptom: a stage frozen at `(k + m) / <small n>` for hours with no error and no driver output. Build the size-info HT and go through `compute_counts_light` + `compute_counts_heavy`, which pick their own partition counts from per-variant contribution; only fall back to the single plan when the heavy set really is empty, and repartition the pair list first if so.
- **`hl.experimental.haplotype_freq_em` will infinite-loop on negative gt_counts.** EM iterations are uncapped, and negative input cells make the likelihood oscillate rather than converge — the symptom is `phase_gnomad.py` stalling for hours on a single partition with no error. Positive-form set algebra can't produce the old complement-bug negatives, but assert `sum(gt_counts_adj) ≤ n_samples` before feeding EM as a cheap guard; `phase_gnomad.py --em-partitions N` bounds worst-case per-partition wall time if a stall slips through.
- **Scratch paths that several jobs share must be unique per invocation.** `phase_from_vcf.call_vcf_chet` wrote its encoder intermediates to a fixed `{tmp_dir}/phase_from_vcf_encoded`, so two extractions running at once clobbered each other's `var_idx.ht`. The visible symptom is a `FileNotFoundException: Item not found: .../var_idx.ht/rows/parts/part-NNN` partway through counting; the dangerous symptom is no error at all, because a job that reads another's variant index just produces wrong counts. It now appends a `uuid4()` suffix. Any helper that writes a named directory under `DEFAULT_TMP_DIR` needs the same treatment before it is run concurrently — `hl.utils.new_temp_file()` does this for you.
- **Pair-count partition defaults are sized for a whole gene and degenerate at locus scale.** `count_all_pairs_auto_split` does `vp_ht.repartition(fallback_partitions)` with a default of **1000** before the indexed count, so repartitioning the pair list on disk cannot help -- it is re-split internally. At PCNT scale (2.9M pairs) that is right; at locus scale (RNU4-2, 60k pairs) it makes partitions of ~60 pairs and the following shuffle fails **non-deterministically** with `HailException: zip: length mismatch: <n>, <m>`, different numbers each run. The numbers changing between runs is the tell that it is a shuffle problem and not the data. Scale the partition count to the pair count: `pcnt_phase_arms.py --count-partitions`, `phase_from_vcf.py --count-partitions` (added for this reason). The existing note above warns about too *few* partitions; this is the opposite failure.
- **Anything calling `encode_genotypes` needs a per-invocation scratch path, not just `phase_from_vcf`.** `pcnt_phase_arms.run_em` had the same fixed-path bug (`{tmp_dir}/pcnt_em_encoded`): two arms run concurrently clobbered each other's `var_idx.ht`, one getting a GCS `412 Precondition Failed` and the other a `zip: length mismatch` from reading a half-rewritten index. Derive the suffix from the output prefix rather than a `uuid4()` where a `--reuse-encoded`-style flag must still find its own previous output.
- **`get_gnomad_v4_genomes_vds` is not a drop-in for `get_gnomad_v4_vds`.** It has no `high_quality_only` (passing it raises `TypeError`), and it forwards `remove_hard_filtered_samples` (default True) to the v3 loader **regardless of `release_only`** — which reads `gs://gnomad-autoclass/sample_qc/ht/genomes_v3.1/gnomad_v3.1_hard_filtered_samples.ht`, present in no bucket. Pass `remove_hard_filtered_samples=False` and supply `filter_samples_ht = meta.high_quality` (safe: high_quality is already non-hard-filtered). Genomes metadata also lacks `project_meta.fixed_homalt_model`. This bit `export_for_phasing`, `create_vp_list --filter-vmt` and `compute_vp_counts --encode-genotypes` separately; the shared fix for the count path is `_count_cohort_vds_kwargs`. Also: no production genomes artifacts exist under `v4.1/variant_cooccurrence/` (exomes only), so scoped genomes runs of `create_vp_list` need `--scoped-inputs`. And `gnomad_qc.v4` `pedigree(finalized=True)` is the *exome* pedigree: its 40,569 trio members match none of the 140,508 high-quality genomes, so the pair list's `in_trios` flag was always False on genomes until `create_vp_list` switched genomes to `gnomad_qc.v3.resources.meta.trios` (`gnomad_v3.1_trios.fam`: one trio per family, 6,743 complete trios, 20,229 members) -- deliberately the same set the genome trio truth uses, so `in_trios` marks exactly the pairs the truth arm can score. Not the full v3.1 `pedigree` (9,160 trios), which would flag pairs carried only by children the truth arm never uses; exomes keep the full finalized pedigree.
- **Keeping read-backed phase (`PGT`/`PID`) requires our own split — `gnomad_qc`'s loader drops it.** `_split_and_filter_variant_data_for_loading` only remaps `{GT, AD, PL}` → local names, so `LPGT` is neither selected pre-split nor produced post-split (and `get_gnomad_v4_vds` also rejects `filter_variant_ht` on unsplit reads). `hl.experimental.sparse_split_multi` itself *does* downcode `LPGT`→`PGT` and pass `PID` through — so `--encode-genotypes` reads `split=False` (samples + intervals only) and calls `_split_variant_data_keeping_phase`, which adds `PGT` to the remap set (matching gnomad_mnv), applies the variant filter itself (locus pre-filter + post-split semi-join), and reconstructs the VDS before `to_dense_mt`. If you switch the encode densify back to `get_gnomad_v4_vds(split=True, ...)`, phase is silently lost and `phased_het` goes empty.
- **The sites HT anchors on the variant-QC final filter of its own data type.** Until 2026-09-30 `--preprocess-sites-ht` hardcoded the *exome* filter HTs (`FINAL_FILTER_ONLY_FILTERS_PATH` / `FINAL_FILTER_PATH`) as the row-set anchor for every data type, so a genomes run kept only the genome variants also called in the exomes -- chr21: 455,011 of 14,001,966 -- and gated them on exome filters. Genomes now anchor on `final_filter(data_type="genomes")` (v4.0, a single table, so no `release_filter_ht` and no `filters_release`). Any genomes sites HT, variant filter HT, filtered VMT or pair list built before that is on the exome variant universe; check `source_paths.filter_ht` in its globals.
- **Per-group logic written as one row expression overflows the JVM class-size limit.** Hail inlines a referenced expression at every use, so a dict-over-groups expression (`gt_counts_by_pop` / `em_by_pop`, ~10 groups) reused across several fields fails at write with `ClassTooLargeException` -- the same limit that made `compute_counts_by_pop` loop over groups. Materialize intermediates in separate `annotate`s and checkpoint between stages (`analysis/grant_resubmission/scripts/em_evidence_failure.py`).
- **Trio truth at chromosome scale dies in the pair join, not the densify.** `call_trio_chet` attaches each variant's phased-het proband array to every pair, twice; on chr21's 5.2M pairs that shuffle failed with `FetchFailedException` (executor gone, stage retried 10 times) after the 2 h 46 m PBT densify had finished. It now first keeps only pairs with a phased-het proband at both endpoints (key-only lookup, checkpointed; lossless, since its last step drops the rest anyway): 981,681 of 4.28M pairs, 8 min. `pcnt_phase_arms.run_trio_truth` had the same fix. The PBT MTs are checkpointed, so a failed `--call-trio-chet` reruns alone.
- **Hail 0.2.134 fails to compile a select that reads both a `Table.group_by().aggregate()` result and a dict built from its `hl.agg.group_by`** (`RuntimeException: stream used in method different from where it was generated -- generated in __m…split_ToArray, used in __m…begin_group_0`). The optimizer fuses the select into the aggregation and the method splitter breaks it, so tiny inputs fail too (the unit test did). Mapping an `hl.agg.array_sum` result in a later `annotate` fails the same way. `merge_subset_counts` checkpoints the aggregated table before building `gt_counts_by_pop`; materialize between the aggregation and any such select. An `hl.agg.take(…, ordering=…)[0]` in a `group_by().aggregate()` whose fields a later `annotate` reads fails the same way (`chr21_merge_beagle_chunks.py`, fixed by the same checkpoint). A tiny local table reproduces it, so test such code locally before a cluster run.
- **`export_for_phasing --adj-only` acts at export, not densify.** A split run (`--checkpoint-mt`, then `--from-checkpoint --out-vcf`) used to need the flag on both invocations; the chr21 production exports passed it only to the densify, so Beagle phased non-adj genotypes as observations. The checkpoint now carries an `export_adj_only` global that the export inherits; a checkpoint written before that makes the export state `--adj-only` or `--no-adj-only`. `phase_from_vcf --adj-mask-mt` still restricts what is *scored* to adj calls either way; the flag decides what the phaser *sees*.
- **gnomad_methods `get_adj_expr` misreads alt-first phased GTs, and v4 exome calls are sometimes phased.** In the raw v4 exomes VDS the local call `LGT` (not just `LPGT`) is phased for `fixed_homalt_model` samples (`LGT == LPGT` wherever `LPGT` is set); every other sample, incl. all UKB, keeps `LGT` unphased. Cause: since GATK 4.0.12.0 (gatk#5318) HaplotypeCaller writes its physical phase into `GT` (alleles reversed when `PGT` is `1|0`, plus `PS`); the GATK 4.1.4.1 / 4.1.8.0 exome samples follow that, the 4.0.10.1 ones predate it. `LA` is a local-to-global allele map with the ref first, not haplotype-ordered: `LA [0, 4]` + `LGT 1|0` = global `4|0`. `sparse_split_multi` maps local alleles onto `[ref, alt]` with `hl.downcode`, which keeps a phased call's haplotype order: raw `LGT 1|0` becomes `GT 1|0` (a phased `1|2` becomes `1|0` for its first alt). `get_het_ab_adj_expr` reads the alt depth as `AD[GT[1]]`, which is the ref depth for `1|0`. VP's adj (and the release freq's, same split) inherits this; it is rare (385 alt-first of 138,186 phased het-ref calls in three surveyed regions, adj flipped on 16) but concentrates in cis double hets. Confirmed on the published v4.1 exome frequencies: recomputing the release's freq step reproduces every adj AC exactly with this reading, and 41 of 6,501 test variants change without it; GATK 4.1.4.1 / 4.1.8.0 samples only, v4 genomes have no phased `LGT`. gnomad_methods 0.9.1 (#849, merged 2026-10-16, what the clusters install from `main`) fixed it (`AD[hl.max(GT[0], GT[1])]`), but **v4 keeps the release's reading** (gnomad_production#2301): every v4 adj goes through `utils.get_v4_adj_expr`, which passes `legacy_het_ab=True`. Don't call `get_adj_expr` directly in v4 code. It needs gnomad_methods ≥ 0.9.1; an older install raises `TypeError` on the flag. See `analysis/phased_gt_adj/REPORT.md`. The high-AB hom-alt correction is unaffected: it exempts `fixed_homalt_model` samples.
- **The raw v4 exomes VDS has 27 duplicated sample IDs (54 columns; 23 IDs are release).** `get_gnomad_v4_vds` drops one copy of each by column index (`ukb_dups_idx_path`, `<s>_<col_idx>`), so a script that reads the raw VDS directly and joins or groups by `s` sees both copies under one ID. Drop them the same way (`add_col_index` on the full `variant_data`, then filter) before comparing with pipeline counts; matching by ID instead cost a carrier or two per pair in the MNV/VP reproduction (`analysis/mnv_vs_vp/reproduce_mnv_vp_phase_5gene.py`).
- **A round-robin `repartition(n, shuffle=True)` straight after a shuffle is indeterminate in Spark.** If an executor is lost mid-stage (a preempted secondary), Spark refuses to retry it and aborts the job: `A shuffle map stage with indeterminate output was failed and retried. However, Spark cannot rollback the ResultStage …`. Checkpoint before such a repartition; `create_variant_pair_filter_ht` (the encode's first step) now does, after it killed a chr21 grant encode on `jg1`.
- **`call_trio_chet` does not scale to a pair list built from the trio members themselves.** It joins each endpoint's whole carrier array onto every pair: on the grant's proband-carried chr21 list (134.7M pairs) that is 29.5 billion carrier records per pass, and its pre-filter removes almost nothing. `call_trio_chet_within_genes` gives the same counts (tested on random trio data, all members and probands only) by self-joining the phased-het carriers on `(gene_id, s)`, so it moves one row per shared carrier. It needs the variant filter HT the within-gene list was built from.
- **The grant's trio truth counted parents.** `pcnt_phase_arms.run_trio_truth` passed the exploded PBT MT straight to `call_trio_chet`, so every trio member's transmission phase (parents: transmitted | untransmitted) counted, unlike `trio_phasing.py --call-trio-chet`, which keeps the probands. All grant truth sets before 2026-10-13 include parents; `--probands-only` gives the production definition. On PCNT it is not a detail: 218,862 of the pilot's 550,327 scored truth pairs (40%) are carried by a parent and no proband, and 94% of them are trans (a parent in trans never passes both variants on), so the pilot truth was 79% trans against 73% for probands only. Both pilots were rebuilt with `--probands-only` and every pilot table re-scored on 2026-10-15 (PCNT 275,459 pairs, RNU4-2 5,886; `pcnt_arms_hq2_probands.trio.ht`, `arms_truth_probands.trio.ht`); use those, not the `*.trio.ht` beside them.
- **Hail 0.2.134 can fail a lookup on a pair table's `(locus1, alleles1)` key prefix** with `HailException: zip: length mismatch: <n>, <m>` -- deterministic, unlike the shuffle one above. It coarsens the right side to `m` prefix-aligned partitions and zips it with the left's `n`; `m < n` when one variant's pairs span a partition boundary, as on the exome pair list cut to PCNT (131 vs 127). Copy the endpoint to new fields, `key_by` them (Hail coerces the sorted data), look up, and `key_by` the pair key back: `analysis/grant_resubmission/scripts/chr21_exome_genome.lookup_endpoint`.
- **A `Table.group_by` over an expensive, un-checkpointed upstream runs that upstream twice.** The shuffle's key-sampling pass evaluates it in full, then the shuffle itself does again. An SV × SNV overlap job (per-entry tests over a dense MT) finished its first full pass after 2 h 40 m and started the second. Checkpoint the per-row result before the group-by.
- **Hail can evaluate a repeated `call[1]` ahead of the guard that protects it.** `&` and `hl.if_else` short-circuit on their own, but when the same `LGT[1]` appears in both a condition and a branch, Hail can evaluate it before the `is_het_ref()` check, and indexing a haploid (sex-ploidy-adjusted) call at `[1]` raises `Index out of bounds for call with ploidy=1`. Compute such an index once, under `hl.or_missing(call.is_het_ref(), ...)`. This crashed nothing on the autosomal test genes; it would have crashed a chrX MNV run.
- **`hl.export_vcf(..., tabix=True)` builds the index on the driver, single-threaded.** For a 13–15 GB chr21 VCF that was 1.5–2 h after the VCF itself had landed, with no progress output (the S1 export and the SV × SNV export both). Budget for it, or index elsewhere (`tabix` in a Batch job) when time matters.
- **On VDS variant data, Hail 0.2.134 crashed (`NullPointerException` while decoding a partition context) on an interval-keyed `Table.index(locus, all_matches=True)` followed by `localize_entries` and per-column array lookups.** `filter_entries` to the entries you need, then `entries()` and a per-sample join, works and is simpler (`analysis/grant_resubmission/scripts/gcnv/exome_cnv_coding_ab.py`). Also cast `add_col_index` results with `hl.int32` before indexing arrays; one path returned int64.
- **`hl.import_vcf` of a large phased VCF defaults to few partitions** (61 for a 1.7 GB, 90,800-sample Beagle chunk: ~70 min, cluster mostly idle). Pass `min_partitions` (500 took it to ~10 min).
- **Concurrent `characterize_chr19_test.py` jobs need their own `--output-dir`.** It is a local dir on the cluster's master, shared by every job there, and `--gcs-out` syncs the whole dir, so the job that finishes last re-uploads its siblings' files, stale ones included. An af-level F5 rerun was overwritten this way by an older job's copy (2026-10-13). Give each job, and above all each rerun, its own `--output-dir`, and a rerun its own `--gcs-out`.
- **A shuffle over tiny partitions can sink the driver.** The S1 Beagle chunk tables (`phase_from_vcf --call-vcf-chet` outputs) hold 185M rows in 50,215 partitions of ~3,700 rows; `chr21_merge_beagle_chunks.py`'s union + `group_by` made that a ~50k × 50k shuffle, and after 4 h on 436 workers the driver died of `OutOfMemoryError` in the scheduler, with nothing written (2026-10-14). Read the partition counts first (`components.partition_counts` in the table's `metadata.json.gz`), coalesce before any shuffle, and skip the shuffle when the inputs are already sorted by the grouping key: the merge now picks each pair's chunk by position and joins only the overlap windows.
- **The in-trans O/E gives partners genes the pair list doesn't.** `run_in_trans_oe.create_clinvar_category_partner_ht` assigns a ClinVar partner every gene of its protein-coding VEP consequences (upstream / downstream included); the variant filter the pair list is built from gives a ClinVar variant only the genes ClinVar names (`_get_clinvar_gene_id_expr`). A partner only the O/E puts in a gene adds to E for every candidate there, but its pairs are never counted, so it can't add to O. chr21: 108 of 1,111 gene × P/LP-partner entries; TTC3's whole E is one PIGP variant (O = 0 on all 17 powered rows). Until it is fixed, leave such partners out of E (`analysis/chr21/calibration/oe_export.py` flags them, `paired`).
- **A TSV written by Python's `csv` module can't carry Hail arrays back.** `csv.DictWriter` wraps a field holding `["CT","C"]` in quotes and doubles the inner ones, and `hl.import_table(types={"alleles": hl.tarray(hl.tstr)})` then reads the column as missing, silently: a (locus, alleles) join matches nothing and a job "succeeds" with zero genotypes (the LoF-pair trio look-up, 2026-10-22, four runs). Write such files with `quoting=csv.QUOTE_NONE, quotechar=None`, or parse defensively (`hl.parse_json` after stripping the quoting).
- **`--with-ld-adjustment` drops partners in repulsion, not coupling.** D′ counts each double het half cis, which halves it (complete coupling → +0.5, complete repulsion → −0.5), and D* thresholds |D′|. On chr21 P/LP rows 99.6% of the E it removes comes from D′ ≤ −0.5: partners with fewer double hets than expected, which includes the trans depletion the test looks for. Coupling is the only LD that should reduce E. See the chr21 report's hypomorph section.

## Dataproc submission

Generic invocation pattern (cluster name and SDK / conda paths are in `CLAUDE.local.md`):

```
hailctl dataproc submit <CLUSTER> \
  --pyfiles=/absolute/path/to/gnomad_chets \
  /absolute/path/to/gnomad_chets/v4/<script>.py -- \
  --gene SGCA --output-postfix sgca_v9_oe_extra_6_12 --overwrite
```

`--pyfiles` zips the repo into the executor classpath so `import gnomad_chets.v4.*` works. **Use absolute script paths** — `hailctl` zips up the repo and changes cwd, so relative paths break.

## Testing

The pytest suite lives in a top-level `tests/` module mirroring the package (like `gnomad_methods/tests/`): `tests/conftest.py` holds a session-scoped Hail fixture and tests are under `tests/v4/`. Run with `pytest tests/` (needs the `gnomad_chets` conda env and `gnomad_chets` importable — i.e. `PYTHONPATH=/path/to/PycharmProjects`, since tests do `from gnomad_chets.v4... import ...`).

- `tests/v4/test_utils.py`, `tests/v4/test_create_vp_list.py` — pure-transform unit tests on tiny `hl.Table.parallelize` inputs; run in seconds against local Spark. `test_create_vp_list.py` covers `assemble_sites_ht` (the `--preprocess-sites-ht` step), incl. the drop-on-InbreedingCoeff-agreement gate.
- `tests/v4/test_create_vp_matrix_unit.py` — pytest units but loads real chr19 fixtures at import (needs GCS/Hail).
- `tests/v4/test_create_vp_matrix.py`, `tests/v4/test_in_trans_oe.py` — `__main__` integration / runnable-script harnesses (not pure unit tests).
